Red-teaming Aegis: attacking my own agent permission system

Connor Evans · Round 1 September 15, 2026 · Round 2 October 19, 2026 · Round 3 October 20, 2026 · full report

Abstract

ONEXUS is a local-first runtime for AI agents. Its arbiter, Aegis, checks every tool call an agent makes against the capabilities the agent declared, and writes each decision to a ledger called Chronicle. It had more than 1,300 tests, all of which checked that it did what it intended. I ran the opposite review: given what the product promises, which guarantees hold when someone is trying to get around them? Round 1 attacked the arbiter’s decisions and found that revoking an agent didn’t stop it. Round 2 attacked the boundary around the arbiter and found that launched agents could read the operator’s secrets and that the ledger could be edited without detection. Round 3 attacked what an agent can do on its own, outside every call it makes to ONEXUS, and found it could read the operator’s files, open its own sockets and write anywhere; agents can now run in a locked-down container behind an egress proxy. In every round the findings were committed before the fixes, so the history proves each gap was real. One finding is left open on purpose, and the report says exactly what the system still doesn’t protect.

1The problem

Most of my work asks one question: how does an AI agent earn permission to act, and how do you stop one that shouldn’t? ONEXUS answers it with a manifest. An agent declares what it needs (file paths, outbound domains, tools) before it runs, and Aegis allows, prompts or denies every call against that declaration. Trust is earned: an agent’s score rises with good outcomes and falls with bad ones, and the score decides how much it can do without asking.

A permission system is worth exactly what its worst case is worth. Testing that it works is the easy half. The half that matters is trying to get around it, and writing down what happened either way.

2Method

Each attack is a test named for the claim it tests. The findings land first in their own commit, asserting the broken behavior, so the suite passes against the code as it shipped and the gap is on record. The fix lands next and flips each finding into a regression test. An attack that fails against the code is recorded too, because a review that lists only wins says nothing about how hard anyone tried.

3Round 1: the arbiter

FindingStatus
F1Revoking an agent didn’t stop it. Revoke set trust to zero but left explicit grants in place, and the arbiter checks grants before it reads trust. A revoked agent kept working.Fixed
F2Trust collapse only fired when an operator lowered the score, not when an agent’s own failures did. Two agents with the same score had opposite containment.Fixed
F3Autonomy is bought with volume. Seven trivial successes from a cold start reach the tier where capabilities auto-grant, and nothing weighs an outcome by what was at stake.Open on purpose
F4The ledger recorded a containment that didn’t happen. After F1, Chronicle showed a clean revoke while the grant was still live.Fixed

F1, F2 and F4 were one bug wearing different clothes: the safety property was attached to a function instead of to the state it protects. The fix moved the grant cleanup behind one helper that every path lowering trust calls, so a score is a score no matter who moved it.

Six attacks held, and they’re why the findings were narrow rather than structural: privileged capabilities never auto-grant, undeclared capabilities are denied even at full trust, unregistered agents are denied, grants don’t cross workspaces, and both ../ traversal and symlink escapes are refused because paths are resolved before they’re compared.

F3 is left open because fixing it properly means risk-weighting outcomes, which is a design decision, not a patch. The report sets out three options, from rate-limiting the climb to requiring a human on the path to the autonomous tier.

4Saying what isn’t protected

Round 1 attacked the arbiter, and the arbiter held. But the report never said where the arbiter stops, and a safety engineer would find the gap in minutes: third-party agents are launched as ordinary child processes, so anything they do outside their calls to ONEXUS never reaches Aegis. So before round 2, I added a threat model and non-goals section that names five gaps with file references, rewrote the README’s claims to match (“governs the calls agents route through ONEXUS” rather than “runs untrusted agents”), and listed the steps that would close them in order.

5Round 2: the boundary

Round 2 took the two gaps that could be closed properly in code and attacked them with real child processes, each reading back what it could see.

AttackBeforeAfter
R2-1A catalog agent reads a secret from the operator’s environment that it never declaredRead itSees nothing
R2-2An agent that declared no keys reads the Anthropic API keyONEXUS handed it overOnly agents that declare it
R2-3An MCP agent with no declared keys reads the same secretRead itSees nothing
R2-4Rewrite a deny to an allow directly in the ledger fileNothing noticedVerification names the row

The first three share one fix: a single function builds every launched agent’s environment from a small baseline (paths, home, temp, locale, no credentials), plus the variables its manifest declares, plus a provider key only when it declares that variable. Tests also check the other direction: a declared variable and a declared key still arrive, and the baseline still lets an agent find its programs.

The fourth chains every new ledger row to the one before it with SHA-256. Verification walks the chain and names the first row that doesn’t follow, which catches an edited, deleted or reordered row. Rows written before the change count as legacy, not tampering, so existing ledgers keep working. Two attacks it can’t catch on its own are truncating the newest rows and recomputing the whole chain; for those, the latest chain value can be recorded somewhere the agent can’t write.

All 1,376 tests passed after round 2, including 23 red-team tests across the first two rounds.

6Round 3: what an agent does on its own

The threat model named one gap above all the others, and round 3 went after it. A catalog agent ran as an ordinary child process of the operator, so anything it did without asking ONEXUS never reached Aegis. Three attacks with real child processes proved it, committed first as findings:

AttackUnconfinedConfined
R3-1 Read a key file in the operator’s home it never declaredRead itSees none of the operator’s files
R3-2 Open a TCP connection to a host it never declaredConnectedNo network, or only declared hosts through the proxy
R3-3 Write a file outside its working directoryWrote itRead-only root; only its own scratch space

The fix lets an adapter declare a container. That agent runs with a read-only root, none of the operator’s files, every capability dropped, a non-root user and resource limits. With no hosts declared it has no network at all. With hosts declared, its only way out is an egress proxy on a private network that tunnels to exactly those hosts, refuses everything else, and logs each decision. The tests run the same attacks inside real containers against a real listener: the declared host is reached through the proxy, an undeclared one gets a 403, and the declared host can’t be reached around the proxy. Every launch now says in the ledger whether it was confined, and one setting refuses to run anything that isn’t.

All 1,386 tests pass after round 3, 33 of them red-team tests.

7What’s still open

  • Only two of the catalog’s 21 hand-written adapters run confined so far: Haystack search and faster-whisper transcription, each with its own image and no network. Building them showed that the other 19 couldn’t run at all, because the server they pointed at had never been written. They’re now marked as planned, the catalog no longer calls them runnable, and ONEXUS refuses to launch them.
  • Agents started from an MCP manifest still run as child processes, with round 2’s environment limits but not round 3’s container.
  • The container uses Docker’s default runtime, not gVisor, and the proxy decides by host name, not by what is sent.
  • F3, the trust ladder that rewards volume over judgment, remains a deliberate design question.

8What I learned

The most useful finding in round 1 wasn’t a bug. It was the shape of the bug: a safety property implemented in one code path is a property of that code path, not of the system. In round 2, the lesson was about claims. The code was honest about its limits in comments, while the README promised more. Writing the threat model first, and making the README say only what the tests prove, was worth more than any single fix. Round 3’s lesson was about coverage: the mechanism took a day, and making every agent use it is the real remaining work, so the report says how many do (two so far) instead of implying all of them.

As with my other work, I built ONEXUS with coding agents. The parts of this study I’d point to as mine are the method (findings before fixes, failed attacks recorded), the decision to leave F3 open rather than patch it, and the choice to publish what isn’t protected.
