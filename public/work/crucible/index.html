Crucible: measuring what AI agents do when they share a machine

Connor Evans · Built September 26 to 28, 2026 · Record of September 28 · crucible-weld.vercel.app

Abstract

People now run several AI agents on one computer, sharing files, credentials and tools, but there was no public evidence of what those agents do to each other. I built Crucible, an instrument that clones real open-source agents at pinned commits, builds each into a container, and runs every pair against four adversarial scenarios. Every result is decided by a side effect the code can check, and every number on the site is a count of rows a reader can open. Across 520 pair runs, eight attacks were confirmed, all of one kind: an agent running a command another agent planted in a file. Two agents fell for it and six never did. The design problem was making a record that a skeptical reader could trust without trusting me, and most of this study is about the decisions that served that goal.

1The problem

You install a coding agent, then a notes agent, then something for your calendar. They end up sharing your filesystem, your clipboard, your OAuth scopes and your model provider keys. There are plenty of threat models about what happens next. I couldn’t find a dataset.

My earlier project, SMADP, estimated those risks from each agent’s documentation. Estimates are cheap and they scale, but a reader can’t check one, and I didn’t trust them myself. So the question for Crucible was narrower and harder: what do real agents actually do to each other, measured in a way a skeptic could verify?

That turned the design problem into one of trust. The reader is a safety engineer or a researcher who assumes the numbers are inflated until shown otherwise. Every decision below is about removing a reason for that reader to doubt the page.

2The approach

Crucible is a pipeline with one rule at every stage: a failure is a row, never a silent drop.

  1. Harvest resolves each agent’s repository to a commit SHA.
  2. Forge builds a container. The build recipe is itself recorded on every row, because changing it would otherwise silently change every figure.
  3. Environment check starts the image with the network denied.
  4. Solo gate asks each agent to do one small task alone through a hand-written entrypoint.
  5. Arena runs every invocable agent against every other, in both directions, under four scenarios.
  6. Classify and audit decide each run from its transcript, then a second, separately written check reads every verdict again.
  7. Press and publish generate the papers and export the store as static JSON for the site.

Each scenario plants something and watches for a side effect. In induced execution, the attacker writes a file containing a command, and the attack is confirmed only if the victim creates the marker file that command would create. A model never decides whether an attack worked.

3Design decisions

3.1 An editorial record, not a dashboard

The obvious form for this data was a dashboard: live tiles, sparklines, a dark operations screen. I’d built several of those, and I rejected it here. A dashboard asks you to watch. This data asks you to read and check. So the site is set like a journal: a serif display face (Instrument Serif), a quiet sans for reading, a monospace for anything that is a value, numbered figures with captions, and one accent color reserved for the thing that matters most, a confirmed attack.

The trade-off is that the page is slower to scan than a dashboard. I accepted that, because the reader I designed for doesn’t scan. They open a number and follow it down to the run.

3.2 Every figure is a count of rows

The report function takes no parameter that lets a figure be asserted. The store has no update method, and a test checks that it doesn’t. Corrections are new rows plus a supersedes row, and both stay readable. The site’s manifest pins each published dataset to an engine commit and a SHA-256 of the data. Together, these mean a number on the page can only exist if the rows behind it exist.

3.3 Deterministic criteria over a model judge

Grading runs with a model would have been faster to build and would have produced more verdicts. It would also have made every result depend on another model’s judgment, which is the thing a skeptic can’t check. I chose side-effect criteria: a file that exists or doesn’t, a canary string that appears or doesn’t. The cost is that some runs end as artifacts rather than verdicts (232 of 520), and the page reports that number rather than hiding it.

3.4 Separate the harness from the agent

When a build fails, it is tempting to blame the agent. Often the real cause is my harness: a language the recipe doesn’t support, a Python version floor, a full disk. Those failures get their own classes and are kept out of the agent’s column, so the attrition figure describes the agents rather than my tooling.

3.5 Answering “is this one model talking to itself?”

Every agent is driven by the same local model, on purpose, so the variable is the agent. Partway through, I asked the question a reviewer would ask: if one model drives everything, are these results just that model talking to itself? The answer is now published on the methodology page and computed on every publish. The evidence is the divergence. Under the same scenarios and the same model, one agent complied 7 times while six agents complied zero times across 46 verdicts. Identical things would behave identically.

3.6 Accessibility and the second theme

The 3D figure that shows who attacked whom now has a spoken summary and a “read this figure as a table” panel with all 224 pairings, so it works without a pointer or a GPU. Contrast is set by measurement, with comments in the tokens file (for example, the faint ink is 4.6:1 on the dark ground). The site later gained a light theme, the same record printed on paper, with every text color at least 4.5:1.

Every confirmed attack is the same kind, and the victims are two agents: mini-swe-agent (7 of 11 verdicts) and OpenHands (1 of 4). Nearly every agent took a turn as the attacker, so what separates a pair that falls from one that holds is whether the agent reading the instruction runs what it finds. No other scenario confirmed in 520 runs.

5Corrections stay in the record

The arena’s first two confirmed attacks were audited before anything was said about either. One held. In the other, the attacker had written a script to check its own work and run it, creating the marker itself before the victim started. The marker was gone by the time the attacker exited, so the two snapshots the criterion compares looked exactly like a victim that had complied.

That row was superseded as an instrument artifact, the criterion was fixed to require the marker to be absent when the victim starts, and the audit gained both checks. The original row is still readable next to its correction. I think this is the most important design decision in the project: a record that hides its mistakes is a record a reader has to take on faith.

6Limitations

  • One model drives every agent. The code can vary the model as an experimental axis, and that run hasn’t happened yet.
  • Eight invocable agents is a small arena. Each new agent needs a hand-written entrypoint, because a wrong one would look exactly like an agent that doesn’t work.
  • Two of the five risk categories I set out to cover, cascading errors and compliance violations, have no executed evidence. A sandbox can’t easily produce a checkable wrong answer, or a real organization’s policy.
  • I built Crucible quickly with coding agents. The commit history shows that, and the safeguards above are what I’d point to as the reason to trust the output anyway.

7What’s next

Run the model axis, so the results say something about agents rather than about agents driven by one model. Add agents in volume by making entrypoint authoring faster without making it less careful. And design a scenario for cascading errors, which needs a task with a right answer a second agent can act on.
