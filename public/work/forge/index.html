The Forge review: approving code a local model wrote

Connor Evans · October 2026 · github.com/AllStreets/ember

Abstract

EMBER is an offline survival console, and its Forge lets a small local model rewrite EMBER’s own code from a plain-language request. Every change has to be approved by a person, and that approval used to run through a chain of browser confirm() popups: long paragraphs, no diff, and an OK button one reflexive Enter away. I redesigned the step where a person decides. It now answers three questions in order: what changed, whether it passed the checks, and how to take it back. One accessible dialog replaced 22 popups, the checks are reported in plain words, the diff is a real line diff, and every save can be undone. I tested it end to end against a real 30B coding model running on the same laptop.

1The problem

Forge is EMBER’s answer to a hard scenario: no internet, no other computer, and a tool that needs fixing. You describe the change, the model writes it, and you approve it. The model is small enough to run on a laptop, so it is sometimes wrong. The approval step is the only thing standing between its output and the files EMBER runs from.

That step was built from the browser’s own popups. This is one of them, word for word, with a typical error filled in:

SYNTAX check FAILED: Unexpected token ‘}’

Apply anyway? A broken file can stop that page (or all of EMBER) from loading. You can restore from _forge_backups/ or the Revert button.

CancelOK

Everything about it works against a careful decision. The question is buried at the end of a paragraph. The popup can’t show the code it is asking about. OK is focused, so Enter saves a file that is known to be broken. And “Revert” names a button somewhere else on the page. There were 22 of these across the Forge (11 alerts, 10 confirms and a prompt): saves, warnings, reverts, a file-name prompt and a reload prompt after every write.

The diff had its own problem. It compared the two files as sets of lines, so it listed every removed line first and every added line after, in the new file’s order. A one-line edit in the middle of a file showed its removal at the top and its addition far below, with no line numbers to connect them.

2Three questions

Someone approving a change a model wrote needs three answers, in this order, before they can say yes with a straight face:

  1. What changed? Which files, and which lines in them.
  2. Did it pass the checks? In words a non-programmer can read, including the checks that didn’t apply.
  3. Can I take it back? Not in theory, but with one button, right after saving.

The review panel is laid out in that order, top to bottom, for every file.

3Design decisions

3.1 One dialog for every question

All 22 popups became one in-page dialog. It is a real dialog: focus moves into it and stays there, Escape always means the cautious answer, and focus returns to whatever opened it. The part I care most about is where focus lands. When the question is risky (“Save a file that fails its checks?”), the safe button has focus, so a reflexive Enter does nothing harmful. Each button also says what it does (Keep reviewing, Save anyway) instead of OK and Cancel.

3.2 Checks in plain words, including the ones that didn’t run

Forge already validated every file: a syntax check, a check that index.html keeps the app’s structure and every script it loads, and a test render of the screen on a hidden page. The old panel collapsed all of that into one pill. Now each check is its own line with a word beside the icon: passed, failed, not run, or not applicable. A stylesheet isn’t syntax-checked, so it says so, rather than claiming “parses cleanly”. A file that fails any check can’t be ticked, and Save stays disabled until something passes.

3.3 A real diff

The new diff trims the lines the two versions share at the start and end, runs a longest-common-subsequence diff on the middle, and shows hunks with three lines of context and both old and new line numbers. A one-line edit now reads as one line, in place.

3.4 Saving is a step you can take back

After a save, a status bar says what was written and offers two things: reload to run it, and undo. Undo restores the backups that save made, and deletes any files Forge created. Before, a failed backup was skipped silently; now it stops and asks, and says that without a backup, Undo can’t restore that file.

4Why review matters

Early on, Forge was asked for a tide-time estimator. The plan had three steps (create the module, add its script tag, add it to the offline cache) and Forge finished only the first, so the file sat on disk, loaded by nothing. It turned up while checking that every cached file existed. Read closely, it was worse than unfinished: estimateTides() ignored the place and date it was given and returned the same two times every day, behind a short delay that made it look like it was calculating.

It looked right at every level you would skim: the module registration, the icon, the form, the error handling. It was hollow exactly where it mattered, so it was deleted rather than wired up (63127c6). On a console built for the day the network is gone, a tide tool that invents times is worse than none.

That is the case the whole design is for. Checks catch code that is broken. Only reading catches code that is fake. So the review can’t be a formality you click through. It has to make reading the change the easy thing to do.

5Testing it for real

I tested the redesign against the real thing rather than a mock. A headless Chromium session pointed Forge at a copy of EMBER in the browser’s private file storage, which uses the same file API, and asked the local qwen3-coder 30B model for a small change. It planned, built and passed every check. Then ⌘↵ saved, Undo restored the file, Escape closed the dialog, and focus went back to the button that opened it, with no page errors. The recording in Figure 1 comes from that run.

6Limits

  • Review is only as good as the reading. The panel makes it easy, but it can’t make someone read.
  • The test render only covers files that are screens; data files and styles get the checks that apply to them, and the panel says which.
  • Saving to disk uses the File System Access API, so Forge works in Chrome, Edge and Brave only. EMBER says so on the Forge page.
  • I built EMBER with coding agents. The parts of this study I’d point to as mine are the three questions, putting focus on the safe answer, and refusing to report a check that didn’t run as one that passed.

7What’s next

The same principles went into loom, which grew out of the Forge. Its permission card now says what a new tool will be able to do, one plain line per grant with how much each matters, shows the code that will run, and says that approving is consent, not a sandbox. Next is the same treatment for edits to loom’s own core, where the stakes are higher and the diffs are longer.
