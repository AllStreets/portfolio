Teardown: taking apart every app on a Mac, and letting you take back what you find

Connor Evans · Built October 19, 2026 · github.com/AllStreets/teardown

Abstract

Apps update themselves, ask for permissions, start helpers at login and leave data behind when they’re deleted, and nothing on a Mac shows what changed underneath or lets you undo it. I built Teardown, a Mac app that reads every installed app the way a reverse engineer would, using Apple’s own command line tools, and explains what it finds in plain English with the evidence beside every claim. It then turns each finding into an action you can take back: roll back an update, revoke a permission, switch off a background service, or move leftovers to the Trash. On my own Mac it found that 20 of 74 installed apps are websites in a wrapper, carrying 21 separate copies of Chromium, that 108 permissions had been granted, and that 56 GB could be freed. No model runs anywhere in it. The design problem was making a forensic read legible to a non-engineer, and then making it safe to act on.

1The problem

Everything a person normally sees about an app is written by someone with an interest in it. Release notes list features. Privacy labels are self-reported. A permission prompt appears once, with no history. Meanwhile the app itself, the bundle on your disk, is a document nobody edits for an audience: it holds the frameworks, the analytics SDKs, the entitlements Apple granted and every web address in the code.

The tools that read bundles exist, but they’re for engineers: codesign, otool, plutil. The question for Teardown was whether that forensic read could be made legible to anyone who has wondered what an app really is, and then useful enough to act on.

2The approach

Teardown is a local engine with a native Mac shell. The engine does the reading; the interface explains and acts.

  1. Read walks each bundle file by file and builds a size map.
  2. Detect names the stack from concrete files: Electron Framework.framework, a Chromium icudtl.dat, the Swift runtime among linked libraries, a Go build ID.
  3. Verify reads the code signature, notarization and entitlements.
  4. Extract finds known SDKs and every web address written into the code.
  5. Snapshot records a fingerprint of each app, plus an APFS clone of it.
  6. Compare diffs every update against the last snapshot.
  7. Act offers an undoable action next to each finding.

The Mac app is a small Rust shell (Tauri) that runs the engine beside it and shows the interface in the system’s own WebKit, so Teardown doesn’t ship a copy of Chromium itself. Pointed at itself, it says so.

3Design decisions

3.1 A radiograph, not a dashboard

My earlier projects were dark dashboards. This subject is forensic: one specimen, examined closely. So each app is drawn as a radiograph on a lightbox. The page opens with a sentence, not a table, saying what the app is in words a non-engineer can repeat. Below it, a radial map of the bundle is labelled like an exploded-view teardown photo: leader lines run from the largest parts out to their names, sizes and share of the app. A percent scale rings the map, because the angle literally is share of bytes, and the bundle identifier runs up the plate’s edge like the codes printed on X-ray film.

The trade-off is that one app at a time is slower than a grid of tiles. The overview page answers the across-my-Mac question instead.

3.2 Evidence, never generation

An AI summary of each app would have read better on the first day. It would also have been a claim nobody could check. Every statement in Teardown is read from a file or a signature, and the plain-English sentences are templates filled with values the tools measured. The interface shows the evidence beside each conclusion, and the README pairs each kind of claim with the Terminal command that reproduces it.

3.3 Every action can be taken back

Turning findings into buttons is only safe if the buttons can be undone, so that became the rule for every action. Rolling back an update restores an APFS clone Teardown kept when it recorded the app; clones share every block with the installed app until it changes, and an 8.8 GB app cloned in 35 MB of metadata. Taking back a permission uses Apple’s tccutil, so the app simply asks again. Startup items are disabled rather than deleted. Clean up only ever moves things to the Trash. Machine-wide changes go through macOS’s own password prompt.

3.4 Read before it runs

macOS tags every downloaded app until it’s opened once. Teardown watches for apps that arrived but never ran and reads them first, so the decision to open one is made with the facts in front of you: where it came from, how it’s built and what it can ask for.

3.5 A tool for agents too

The engine is also an MCP server, so an assistant like Claude can ask which apps can record the screen or what changed in the last update. It can revoke a permission or roll an app back, but only after the person agrees.

5What I got wrong

Running Teardown on a real Mac surfaced four wrong answers, and each changed the design rather than just the code.

  • Unfair labels. Chrome and Acrobat were first counted as “web pages in a wrapper.” They embed or are browsers, so they now get their own group.
  • False alarms. After I taught the engine to read iPhone apps, five of them showed fake “updates,” because their earlier snapshots had been read as empty. Snapshots now record which engine version took them, and an improved engine re-baselines silently.
  • The wrong owner. Microsoft Teams’ updater was credited to Visual Studio because both share a vendor prefix. An item is now credited to an app only when its name points at that app.
  • Lost trust. Every rebuild gave the app a new fingerprint, so macOS dropped its Full Disk Access each time. Signing with a stable local certificate keeps Teardown’s identity across rebuilds.

A tool that tells you what your apps are doing has to be right about small things, or it won’t be believed about big ones. The same instinct changed the unused-apps judgment: Spotlight had no record for most apps after a Mac migration, so Teardown reads when an app last wrote to its own data and says “last activity Teardown can find” rather than claiming certainty.

6Limitations

  • It can’t block an app’s network traffic. That needs a network extension signed by Apple, and I’d rather say so than fake it.
  • Apps containing files only an administrator can read can’t be cloned, so they can’t be rolled back.
  • There is deliberately no signed download: Teardown is built from source you can read. That keeps trust simple and limits who can try it.
  • I built Teardown in a day with coding agents. The evidence table and the undo on every action are what I’d point to as the reason to trust it anyway.

7What’s next

Read disk images before they’re installed, not just apps after they land. Grow the agent tools beyond the first nine. And track changes across several Macs in a household, so one person can see what updated on everyone’s machines.
